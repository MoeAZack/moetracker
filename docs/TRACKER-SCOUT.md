# VALORANT ranked-tracker scout

Research checked 2026-10-12 (Cairo). Scope: a single private team; players opt in; coach/owner see the team; no paid-provider authorization. “Free” below means only what the cited source currently states, not a guarantee.

## Decision

**Build the product around a provider-neutral sync contract, but do not call the current Henrik feed approved.** The clean destination is Riot production API + RSO. Riot exposes match-by-ID and matchlist-by-PUUID, while player stats/history require opt-in; however VALORANT has no personal keys, RSO is only for approved production apps, and Riot lists “apps that are not public and are designed for personal use only” as unapproved. A private-team-only pitch therefore has a real approval risk ([Riot VALORANT policy](https://developer.riotgames.com/docs/valorant), [Riot FAQ](https://developer.riotgames.com/docs/faqs)).

Keep the existing Henrik path disabled for new automatic ingestion until provider terms, policy applicability and consent are resolved. An **experimental/unofficial** flag or player consent alone is not proof of Riot authorization; never collect Riot passwords/tokens. Henrik can technically supply rank/RR and recent history, but its own repository says it uses the in-game API, is not Riot-endorsed, and is not intended for large production use ([Henrik README](https://github.com/Henrik-3/unofficial-valorant-api)). Do not promise availability or Riot approval.

## Safe automatic personal sync contract

1. Each player must explicitly link/consent; record consent version/time and allow unlink + deletion. Owner/coach access is team-scoped; teammates get the simpler visibility chosen by the player/team. Never discover hidden profiles or pre-match opponents.
2. Store `provider`, PUUID, shard/region (`americas`, `europe`, `asia` routing as applicable), last successful cursor/time, and provider response version. Keep secrets server-side; never accept Riot username/password, cookies, entitlement JWTs or lockfiles.
3. Poll after a plausible match completion plus a conservative periodic fallback. Honor `429` and `Retry-After`, exponential backoff with jitter, per-player serialization, a global provider budget, and circuit breaking. Do not poll all players on page load.
4. Fetch newest-first until the saved match ID/cursor, stop on overlap, and upsert idempotently by `(provider, matchId, puuid)`. Recompute derived W/L/RR only from complete accepted records. Preserve last-good data on partial/provider failure.
5. Rank tier/RR is a timestamped observation, not ground truth. Riot match rows can lag promotions by one game; Tracker likewise documents that limitation. Show `last synced`, provider, completeness, and stale/error state.

## Existing `henrikSyncPlayer` repairs before any use

The current path reads `HENRIK_API_KEY`, calls MMR v3 and stored-matches v1 (`size=20`), and writes broad player/match state. Repair it to: require recorded consent; make region explicit; use Cairo day boundaries where product logic says “today” (not UTC); retain last-good W/L on failure instead of writing zeroes; paginate/cursor beyond a fixed 20; deduplicate by match ID; separate fetch/validate from a narrow transaction; expose stale/partial status; and add 429/backoff/circuit-breaker behavior. Keep the provider swappable and label all Henrik-derived data unofficial.

**Go/no-go:** proceed with UI/schema, mock fixtures, metadata cache, consent and sync infrastructure. Do **not** activate or represent ranked ingestion as production-ready until an eligible source, applicable permissions and consent are established. An owner risk acceptance is not a substitute for required provider authorization. No login scraping, credential APIs, new third-party uploads, paid provider, or GRID application is authorized by this scout.
